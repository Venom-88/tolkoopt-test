# Тестовое задание ТОЛЬКООПТ — Python-разработчик

## 1. Вопросы к задаче

1. Как товары конкурентов сопоставляются с нашими: по бренду и артикулу, с учётом кроссов? Кто проверяет ошибки сопоставления?
2. Какие изменения цены можно применять автоматически, а какие — только после проверки менеджером? Кто принимает решение, если цена ушла неверная?
3. Как система прайс-листов сейчас получает результат проценки: кто загружает Excel, в каком формате? Можно ли писать в её базу или API напрямую?
4. Если площадка недоступна или отдала часть данных — считать по остальным, брать её прошлые данные или не менять цену?
5. Сколько позиций и какие площадки ключевые? Выдержит ли каждая площадка опрос раз в час (защита, прокси, капча)?

**Самые важные — 2 и 3.**
- **Вопрос 2** задаёт защиту от неверных цен: пороги автоприменения, что уходит на ручную проверку и нужен ли на старте вообще автоматический режим. Без этого включать «каждый час автоматически» рискованно.
- **Вопрос 3** задаёт точку интеграции и способ запуска рядом со старой системой. Если прайс-листы могут читать цены из таблицы PostgreSQL — пишем туда, переключение флагом. Если только Excel — сначала новая платформа выдаёт Excel того же формата, и действующая система вообще не меняется.

**Допущения:** сопоставление по бренду и артикулу уже делает новая платформа; система прайс-листов (FastAPI + PostgreSQL) может читать цены из отдельной таблицы; автоматически применяем изменения до 30%, больше — ручная проверка (как в starter.py); сервер с Docker и PostgreSQL уже есть.

## 2. Архитектура

```
Планировщик (раз в час, run_id)
  → Сборщики по площадкам (asyncio, httpx/Selenium, тайм-аут, ретраи)
  → PostgreSQL: сырые предложения + статус площадки
  → Проверка качества → recommend_price → APPLY / REVIEW / HOLD + причина
  → APPLY: в систему прайс-листов | REVIEW: менеджеру | HOLD: цена не меняется
  → Алерты в Telegram
```

1. **Планировщик** — фоновый воркер, раз в час создаёт запуск с run_id. Если прошлый запуск ещё идёт, новый не стартует (блокировка в PostgreSQL).
2. **Сборщики** работают параллельно, по одному на площадку, с тайм-аутом. Падение одной площадки не останавливает остальные.
3. **Хранение:** сырые предложения пишутся в PostgreSQL вместе со статусом площадки и временем. По ним видно, откуда взялась цена, — можно ответить менеджеру «почему цена такая».
4. **Пригодность данных:** площадка вернула success, данные свежие (этот запуск), цены больше нуля, число предложений не упало резко к прошлому запуску. Резкое падение обычно значит, что площадка сменила вёрстку и парсер собрал мусор.
5. **Расчёт** — recommend_price по каждой позиции. Цена, решение и причина сохраняются в таблицу решений.
6. **Площадка недоступна:** помечается error, позиции, где она участвовала, получают HOLD, остальные считаются как обычно. Если площадка лежит два запуска подряд — алерт.
7. **Повторная обработка:** у записей уникальный ключ (run_id, площадка, товар), повтор перезаписывает, а не дублирует. Публикация задаёт цену значением, а не «изменить на X», и опубликованный run_id отмечается — второй раз не публикуется.
8. **Запуск рядом со старой:** 1–2 недели теневого режима — новая платформа считает каждый час, но ничего не публикует. Каждый день сверяю её цены со старой проценкой и разбираю расхождения с автором. Затем автопубликация для одной категории, потом для всех.
9. **Откат:** старая система не выключается. Источник цен для прайс-листов — флаг в настройках; при проблеме переключаю на старый, а цены последнего запуска возвращаю по истории решений.
10. **Новых сервисов не добавляю:** PostgreSQL, воркеры и Docker уже есть. Redis или Kafka при запуске раз в час не нужны — их роль выполняет таблица запусков. Такое решение я смогу сопровождать один.

## 3. Исправление кода

Что было не так в `recommend_price`:
- не было тайм-аута, исключения роняли расчёт, статус источника не проверялся — `partial` и `error` считались нормальными данными;
- `delivery_days = None` вызывал ошибку при сравнении с 6;
- собственный магазин MYSHOP не исключался;
- деньги считались во `float`, а `round()` округляет до ближайшего, а не вниз;
- `min_price` не учитывался;
- при пустом списке `min()` падал с ошибкой;
- решение всегда APPLY, без проверки на 30%.

Исправлено: `asyncio.wait_for` (работает с Python 3.10), только `Decimal` с `ROUND_FLOOR`, сравнение на 30% без деления — поэтому граница «ровно 30%» считается точно.
